3. Compiler

`gcc -std=gnu17 -S main.c -o main.s`

Ищем `main`

`grep -n "main" main.s`

Скомпилируем программу с разными уровнями оптимизации:
`O0` = без оптимизаций
`O1` = базовые оптимизации, небольшой рост времени компиляции
`O2` = относительно агрессивная оптимизация, стандарт в продакшн коде
`O3` = агрессивная оптимизация

Собрать код на архитектуре aarch64 (в образе Debian):

`gcc -std=gnu17 -O0 -S main.c -o main.s`

`gcc -std=gnu17 -O2 -S main.c -o main_O2.s`

Сравним их:

`diff -u main.s main_O2.s`

Исходный код на C не определяет конкретную последовательность машинных инструкций. Компилятор оптимизирует программу с учётом выбранных флагов и целевой архитектуры.

Скомпилируем `foo.c` с разными уровнями оптимизациями и сравним:

`gcc -O0 -S foo.c -o foo_O0.s`

`gcc -O2 -S foo.c -o foo_O2.s`

Чтобы скомпилировать программу в ассемблерную для архитектуры х86-64, надо использовать кросс-компилятор; он уже установлен в образе:

`x86_64-linux-gnu-gcc -S -masm=intel main.c -o main.S`

Информация о файле

- тип содержимого файла (обычно не по расширению, а по магическим байтам)
- например, ELF-файл начинается с байтов `7f 45 4c 46`, где `45 4c 46` — ASCII "ELF".
- LSB (least significant byte first) = little endian
- relocatable = object file, not app

Объектный файл содержит:
- машинный код;
- таблицу символов;
- информацию о секциях;
- relocation entries (места, которые линкеру нужно исправить после компоновки объектных файлов)
- ссылки на функции/переменные, адреса которых ещё не определены окончательно.

Отличия объектного файла от исполняемого файла:

- секции объектного файла не размещены в памяти, то есть для них не указаны адреса в оперативной памяти, по которым они должны размещаться при выполнении программы

- так как секции не размещены в памяти, машинный код функций содержит «предварительные» адреса, которые должны быть исправлены (релоцированы) при размещении секции в памяти;

- у объектного файла нет точки входа, с которой должно начаться выполнение программы.

Посмотреть информацию о файле:

`file main.o`

`objdump -f math.o`

- `HAS_RELOC` - есть релокации
- `HAS_SYMS` - есть таблица символов

Посмотреть таблицу секций (в одну секцию группируются логически близкие сущности программы)

`objdump -h main.o`

Другая команда:

`readelf -S main.o`

Секции файла могут быть:

- `.text` -  машинный код

- `.data` - инициализированные глобальные / статические данные

- `.bss` - неинициаилизированные глобальные / статические данные

- `.rodata` - константные данные

- `.symtab` - таблица символов

- `.strtab` - строки, используемыее таблицей символов

- `.rela.text`, `.rela.data` - relocation entries

- `text.startup` - тут содержится `main`


Обратим внимание, что секции не имеют адресов в программе (VMA и LMA имеют нулевые значения)

Свойство `CONTENTS` означает, что содержимое секции хранится в объектном файле реально; например, у `.bss` нет этого свойства, поскольку для неё достаточно знать только суммарный размер секции.

`.comment` не обладает свойствами `ALLOC` и `LOAD`, то есть эта секция находится только в объектном файле, под содержиоме секции не выделятеся оперативная память и оно не грузится из объектного файла в память.

Посмотреть содержимое секции `.rodata`:

`objdump -j .rodata -s main.o`

Посмотреть таблицу символов:

`readelf -s main.o`

`objdump -t main.o`

Тут:

format:
- l = local
- g = global

Первый стобец - адрес в памяти; видим, что он не назначен ни одному символу. 

Пятый столбец - размер символа

Что видим:

`static_local_var.0`, `static_global_var` - локальные символы (`l`), а `global_init_var`, `global_var` - глобальные (`g`)

`static` задаёт статический класс памяти 

Посмотреть символы файла

`nm main.o`

`T` — функция/символ, определённый здесь;
`U` — undefined symbol, который должен быть разрешён linker'ом.
`r` - relocation entry

Посмотреть relocation entries:

`readelf -r main.o`

или

`objdump -r sum.o`

Здесь:
`Offset` — где в секции находится поле, которое надо исправить; смещение от начала секции
`Type` — как именно вычислять новое значение (`_PC32` = 4 байта);
`Sym. Name` — относительно какого символа производится relocation;
`Addend` — дополнительная константа в формуле.

Посмотреть содержимое секции `.text` в виде инструкций ассемблера:

`objdump -j .text -D main.o`

Видим, что все созданные нами в программе сущности являются определёнными в итоговом исполняемом файле.

Виды исполняемых файлов:

- динамически скомпонованный файл:

  - требуют для работы динамические библиотеки, которые должны быть загружены в память программы

  - при запуске программы в память загружается динамический загрузчик (в Linux - интерпретатор); он подгружает в память динамические библиотеки, перечисленные в исполняемом файле, а после связывает символы из файла и библиотек

  - `ldd app` - список динамических библиотек, необходимых для работы программы

  - неперемещаемый:

    - расчитан на загрузку в память с определённого фиксированного адреса (зависит от архитектуры)

    - традиционно все исполняемые файлы в Linux

    - `objdump -f app` -> start address + `EXEC_P` = подготовлен к исполнению

    - `objdump -h app` - смотрим секции:

      - секции получили адреса

      - `objdump -j .interp app` - увидим адрес динамического загрузчика

    - в исполняемой программе таблица символов не нужна -> удалить её `strip -s app`

    - `objdump -T app` - динамическая таблица символов:

      - `*UND*` - символы должны быть найдены в подгружаемых динамических библиотеках при старте программы

      - по умолчанию, отсутствуют глобыльные переменные и функции -> нужно компилировать с опцией `-rdynamic`

    - `-Wl,-Ttext-segment=100000` - поменять стартовый адрес программы на x86-64 на `1000000` 

  - перемещаемый:

    - подгружается в память по новому случайному адресу

    - не отличаются от разделяемыых объектных файлов ничем кроме наличия прописанного динамического загрузчика

    - компилировать с флагами `-fPIE -pie`: `-fPIE` - генерировать код ассемблера для позиционно независимых файлов (position independent executable), `-pie` - для компоновщика сделать на выходе перемещаемый исполняемый файл

    - `objdump -f app` -> `DYNAMIC` = адрес размещения программы в памяти должен быть определён при загрузке программы в память

    - `objdump -h app` -> адреса секций даны в предположении, что программа начинается с нулевого адреса

- статически скомпонованный файл:

  - не требует загрузки динамических библиотек, расчитан на загрузку с фиксированного адреса

  - может не иметь таблицы символов, к тому же она и не нужна -> удалить её `strip -s app`

  - компилировать с флагом `-static`

  - файл большого размера, так как код всех библиотек непосредственно вставляется в исполняемый файл

  - требуется статическая версия стандартной библиотеки С - `libc.a` - по пути `usr/lib64`; `.a` - архивные / библиотечные файлы (в Windows - `.lib`)

  - архивные файлы являются архивами из объектных файлов, снабжены своей таблицей символов

  - `objdump -f /usr/lib64/libc.a` - заголовок архива

  - `ar r libsum.a sum.o` - добавить / заменить объектный файл в архиве

- разделяемый объектный файл (shared object), то есть динамическая библиотека:

  - в отличие от перемещаемого исполняемого файла предназначен для загрузки в память других программ, поэтому не имеет точки входа, даже если текст программы содержит `main`

  - компилировать с флагами `-fPIC -shared`: `-fPIC` - генерация позиционно независимого ассемблерного кода; `-shared` - компоновщик должен создать разделяемый объектный файл

  - `objdump -f app` -> как у перемещаемого объектного файлоа, только start point = 0


Преимущества динамической компоновки:

- код библиотеки один раз загружен в память и используется всеми процессами в системе

- исполняемый файл меньшего размера

- независимое обновление динамической библиотеки, исполняемые файлы исползуют её новую версию

Недостатки динамической компоновки:

- зависимость от динамических библиотек, которые могут зависеть от ОС; для максимальной переносимости стоит компоновать программы статически

Декомпозиция проекта

- разбиение программы на **модули** - единицы организации кода, которые объединяют схожую функциональность, предоставляют определённый интерфейс использования этой функциональности другими модулями

- в языках C и C++ модули реализуются с помощью концепций заголовчных (`.h`, `.hpp`) и файлов реализации (`.c`, `.cc`, `.cpp`): заголовчные файлы обрабатываются препроцессором и включаются в исполняемые файлы, а файлы реализации компилируются в объектные файлы и потом линкуются в исполняемый файл

Предопределённые макросы:

- `__LINE__` - номер строки, в которой используется макрос

- `__FILE__` - имя файла, просматриваемого в данный момент времени препроцессором

- `__DATE__` -  время компиляции

Макросы, зависящие от трансплятора:

- `__GNUC__` - версия компилятора gcc

- `__linux__` - равен 1, если компиляция в Linux происходит


Макрос с произвольным числом аргументов:

GNU Make

- отслеживание зависимостей одних файлов от других

- выявление "устаревших" файлов и выполнение команд для их обновления

- **проект** - совокупность файлов, зависящих друг от друга

- **файл описания проекта** перечисляет зависимости между файлами и задаёт команды для обновления зависимых файлов (по умолчанию, называется `Makefile` или `makefile`)

- `make Makefile` - запуск команд 

- http://www.gnu.org/software/make/ 

- Файл A зависит от файла B, если для получения файла A необходимо выполнить некоторую команду над файлом B; например, объектный файл `main.o` зависит от файла реализации `main.c`

- Синтаксис `Makefile`:

`VAR_NAME` = `VAR_DEF` - определение переменной

`${VAR_NAME}` или `$(VAR_NAME)` - использование переменной

переменные рассматриваются как макросы

Специальные переменные:

`$@` - имя цели, стоящей в левой части правила

`$<` - имя первой зависимости в правой части правила

`$^` - список всех зависимостей в правой части правила

Зависимости определяются так:

`TARGET: TARGET_1 TARGET_2 ... TARGET_N`

`TARGET` - имя файла или имя, обозначающее действие (`clean`)

После описания зависимости идут команды для перекомпиляции цели; каждая команда должна начинаться с табуляции (`\t`)

Пусть проект состоит из трёх файлов: `main.c`, `math.c`, `foo.c`, при этом для `math.c` есть ещё заголовочный файл `math.h`.

Тогда Makefile может быть таким (см. код):

  - первой в списке пишут главную цель

  - чтобы не пришлось пересобирать все файлы в случае изменения одного, в качестве целей указывают объектные файлы

  - `make main.o` - пересобрать конкретную цель; если не указать цель, то берётся самая первая в списке

  - по правилам принято задавать две цели: `all` - главная цель, ради которой создаётся `Makefile`, и `clean` - удалить временные рабочие файлы (исполняемый файл, объектные файлы и тд)

Придадим Makefile'у более общий вид (см код). 

Теперь можно так запустить:
```
make CC=clang
make CFLAGS="-g" LDFLAGS="-g"
```

Задание шаблоныхх правил:
```
%.o : %.c:
	$(CC) -c $(CFLAGS) $<
```

Командные интерпретаторы

- Скрипт командной оболочки начинается со строки `#!/usr/bin/env bash` = запуск программы интерпретатора `bash`, на вход которой передаётся имя текущего скрипта; эта программа может располагаться по разным путям, утилита `env` ищет поиск интерпретатора в переменной окружения `PATH` и запускает программу, переданную ей в качестве аргумента

- `/bin/sh` - общий предок вех интерпретаторов

- `man builtins` - список встроенных команд интерпретатора

- `$'\n'` - специальное экранирование символа переноса строки

В скриптах используются три вида кавычек, которые имеют различное семантическое назначение:

- 'одинарные кавычки' — сохраняет текст без изменений;

- \``обратные одинарные кавычки`\` (backticks) — выполняют команду, и результатом является вывод этой команды;

- "двойные кавычки" — внутри них возможно экранирование символом \, подстановка значений переменных (начинаются с символа $), и возможно выполнение команд с помощью вложенных \``обратных кавычек`\`.

- `var=value` (без пробелов)

- `$var`, `${var}` - использование

- Использование несуществующей переменной не приводит к ошибке, будет просто пустое значение.

- Если необходимо сохранить вывод команды в переменную, то используется один из двух способов:

  - \``обратные одинарные кавычки`\`, между которыми   заключена команда и ее аргументы;

  - заключение в конструкцию `$()`.

- `$?` - целочисленный код возврата последней команды

- `$0`...`$9` — аргументы команды от 0 до 9, при этом `$0` - имя самого скрипта

- `$#` — целочисленное значение количества аргументов

- `$@` — список всех аргументов, начиная с первого

- `$*` — строка, которая содержит список всех аргументов, начиная с первого.

Функции можно задавать синтаксически тремя разными способами, самый универсальный - такой:
```
# 1. Только имя и скобки
very_important_function() {
   # реализация функции
}
```

`|` - конвейер команд / pipe - передача вывода одной функции в качестве входа другой

Условное выполнение последовательности команд:

- `cmd1 && cmd2` - `cmd2` будет выполнена, если `cmd1 `выполнена успешно (= `$?` равен 0), а итоговый результат — это код возврата `cmd2`;

- `cmd1 || cmd2` - `cmd2` будет выполнена, если не удалось успешно выполнить cmd1 (= `$?` не равен 0), результат — либо значение 0, либо код возврата `cmd2`

- `true` -> 1, `false` -> 0
```
rm -f файл_который_не_существует || true  # всегда будет успешный код возврата
```

- Аргумент `if` - любая команда; если команда возвращает 0, то условие `if` считается истинным
```
$x -eq $y - истина, если значения $x и $y равны;

$x -ne $y - истина, если значения $x и $y не равны;

$x -gt $y - истина, если значение $x > $y;

$x -lt $y - истина, если значение $x < $y;

$x -ge $y - истина, если значение $x >= $y;

$x -le $y - истина, если значение $x <= $y;

-n $str - истина, если строка $str не пустая;
-z $str - истина, если строка $str пустая;

$str1 = $str2 - истина, если строки $str1 и $str2 равны;

-e $pathname - истина, если существует путь $pathname;

-f $filename - истина, если существует обычный файл $filename;

-d $dirname - истина, если существует каталог $dirname;

-x $filename - истина, если существует обычный файл $filename, и он является выполняемым.
```

Hometask

Условие:

В первой строке стандартного потока ввода подаются числа $N$ ($0 < N <= 20000$) и $M$ ($0 < M < 2^{31}$). 

Числа $N$ и $M$ записываются в десятичной системе счисления. 

В следующей строке следуют $N$ 32-битных целых неотрицательных чисел $a[i]$ ($0 <= a[i] < M$). 

Числа записываются в десятичной системе счисления. 

Далее до конца файла следуют числа $x[j]$ ($0 <= x[j] < M$).

Числа записываются в десятичной системе счисления. 
 
Каждое число записывается на отдельной строке.

Пусть $K$ — количество чисел $x$ во входном потоке. 

Тогда на длину ввода выполняется ограничение $0 <= N * K < 2000$. 

Для каждого числа $x[j]$ вычислите и выведите на стандартный поток вывода значение $\sum_{i = 0}^{i < N}(a_i * x_j^{N - 1 - i})$. 

Все вычисления проводите по модулю $M$. 

Число выводите в десятичной системе счисления.


Вы должны использовать встроенную целочисленную арифметику bash. 

Вызывать внешние программы нельзя.


Решение

Использовать схему Горнера: для каждого $x$

$a_0 * x^{N - 1} + a_1 * x^{N - 2} + ... + a_{N - 1}$

вычисляется как последовательное

$r <- (r * x + a_i) \mod M$

Это даёт $O(N)$ на один $x$, а по условию $N * K < 2000$, поэтому более чем достаточно

Почему это работает:

Пусть $P(x) = a_0 * x^{N - 1} + a_1 * x^{N - 2} + ... + a_{N - 1}$, тогда схема Горнера переписывает это выражение:

$P(x) = (((a_o * x) + a_1) * x + a_2) * x + ... +a_{N - 1}$

По условию $0 <= x < M < 2^{31}, 0 <= result < M$, поэтому `result` $* x < (2 ^ {31} - 1)^2 < 2^{62}$

$a[i] < 2^{31}$, следовательно, в `result` не будет переполнения для bash с 64-битным целочисленным типом
