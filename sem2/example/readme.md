Commits:

1. gcc

`gcc -std=gnu17 main.c math.c -o app`

Посмотреть, какие команды gcc запускает под капотом:

`gcc -std=gnu17 -v main.c math.c -o app`

`gcc -std=gnu17 -### main.c math.c -o app`

2. Preprocessor

Добавим директивы в `main.c`

`g++ -E main.c -o main.i`

Посчитать число строк в файле:

`wc -l main.c`

`wc -l main.i`

3. Compiler

`gcc -std=gnu17 -S main.c -o main.s`

Ищем `main`

`grep -n "main" main.s`

Скомпилируем программу с разными уровнями оптимизации:
`O0` = без оптимизаций
`O1` = базовые оптимизации, небольшой рост времени компиляции
`O2` = относительно агрессивная оптимизация, стандарт в продакшн коде
`O3` = агрессивная оптимизация

Собрать код на архитектуре aarch64 (в образе Debian):

`gcc -std=gnu17 -O0 -S main.c -o main.s`

`gcc -std=gnu17 -O2 -S main.c -o main_O2.s`

Сравним их:

`diff -u main.s main_O2.s`

Исходный код на C не определяет конкретную последовательность машинных инструкций. Компилятор оптимизирует программу с учётом выбранных флагов и целевой архитектуры.

Скомпилируем `foo.c` с разными уровнями оптимизациями и сравним:

`gcc -O0 -S foo.c -o foo_O0.s`

`gcc -O2 -S foo.c -o foo_O2.s`

Чтобы скомпилировать программу в ассемблерную для архитектуры х86-64, надо использовать кросс-компилятор; он уже установлен в образе:

`x86_64-linux-gnu-gcc -S -masm=intel main.c -o main.S`

4. Assembly

Добавим сперва несколько глобальных и статических переменных в `main.c`

`gcc -std=gnu17 -c main.c -o main.o`

`gcc -std=gnu17 -c math.c -o math.o`

Информация о файле

- тип содержимого файла (обычно не по расширению, а по магическим байтам)
- например, ELF-файл начинается с байтов `7f 45 4c 46`, где `45 4c 46` — ASCII "ELF".
- LSB (least significant byte first) = little endian
- relocatable = object file, not app

Объектный файл содержит:
- машинный код;
- таблицу символов;
- информацию о секциях;
- relocation entries (места, которые линкеру нужно исправить после компоновки объектных файлов)
- ссылки на функции/переменные, адреса которых ещё не определены окончательно.

Отличия объектного файла от исполняемого файла:

- секции объектного файла не размещены в памяти, то есть для них не указаны адреса в оперативной памяти, по которым они должны размещаться при выполнении программы

- так как секции не размещены в памяти, машинный код функций содержит «предварительные» адреса, которые должны быть исправлены (релоцированы) при размещении секции в памяти;

- у объектного файла нет точки входа, с которой должно начаться выполнение программы.

Посмотреть информацию о файле:

`file main.o`

`objdump -f math.o`

- `HAS_RELOC` - есть релокации
- `HAS_SYMS` - есть таблица символов

Посмотреть таблицу секций (в одну секцию группируются логически близкие сущности программы)

`objdump -h main.o`

Другая команда:

`readelf -S main.o`

Секции файла могут быть:

- `.text` -  машинный код

- `.data` - инициализированные глобальные / статические данные

- `.bss` - неинициаилизированные глобальные / статические данные

- `.rodata` - константные данные

- `.symtab` - таблица символов

- `.strtab` - строки, используемыее таблицей символов

- `.rela.text`, `.rela.data` - relocation entries

- `text.startup` - тут содержится `main`


Обратим внимание, что секции не имеют адресов в программе (VMA и LMA имеют нулевые значения)

Свойство `CONTENTS` означает, что содержимое секции хранится в объектном файле реально; например, у `.bss` нет этого свойства, поскольку для неё достаточно знать только суммарный размер секции.

`.comment` не обладает свойствами `ALLOC` и `LOAD`, то есть эта секция находится только в объектном файле, под содержиоме секции не выделятеся оперативная память и оно не грузится из объектного файла в память.

Посмотреть содержимое секции `.rodata`:

`objdump -j .rodata -s main.o`

Посмотреть таблицу символов:

`readelf -s main.o`

`objdump -t main.o`

Тут:

format:
- l = local
- g = global

Первый стобец - адрес в памяти; видим, что он не назначен ни одному символу. 

Пятый столбец - размер символа

Что видим:

`static_local_var.0`, `static_global_var` - локальные символы (`l`), а `global_init_var`, `global_var` - глобальные (`g`)

`static` задаёт статический класс памяти 

Посмотреть символы файла

`nm main.o`

`T` — функция/символ, определённый здесь;
`U` — undefined symbol, который должен быть разрешён linker'ом.
`r` - relocation entry

Посмотреть relocation entries:

`readelf -r main.o`

или

`objdump -r sum.o`

Здесь:
`Offset` — где в секции находится поле, которое надо исправить; смещение от начала секции
`Type` — как именно вычислять новое значение (`_PC32` = 4 байта);
`Sym. Name` — относительно какого символа производится relocation;
`Addend` — дополнительная константа в формуле.

Посмотреть содержимое секции `.text` в виде инструкций ассемблера:

`objdump -j .text -D main.o`

5. Linkage

`gcc main.o -o app` -> error

`gcc main.o math.o -o app`

`./app`

`nm app`

Видим, что все созданные нами в программе сущности являются определёнными в итоговом исполняемом файле.

Виды исполняемых файлов:

- динамически скомпонованный файл:

  - требуют для работы динамические библиотеки, которые должны быть загружены в память программы

  - при запуске программы в память загружается динамический загрузчик (в Linux - интерпретатор); он подгружает в память динамические библиотеки, перечисленные в исполняемом файле, а после связывает символы из файла и библиотек

  - `ldd app` - список динамических библиотек, необходимых для работы программы

  - неперемещаемый:

    - расчитан на загрузку в память с определённого фиксированного адреса (зависит от архитектуры)

    - традиционно все исполняемые файлы в Linux

    - `objdump -f app` -> start address + `EXEC_P` = подготовлен к исполнению

    - `objdump -h app` - смотрим секции:

      - секции получили адреса

      - `objdump -j .interp app` - увидим адрес динамического загрузчика

    - в исполняемой программе таблица символов не нужна -> удалить её `strip -s app`

    - `objdump -T app` - динамическая таблица символов:

      - `*UND*` - символы должны быть найдены в подгружаемых динамических библиотеках при старте программы

      - по умолчанию, отсутствуют глобыльные переменные и функции -> нужно компилировать с опцией `-rdynamic`

    - `-Wl,-Ttext-segment=100000` - поменять стартовый адрес программы на x86-64 на `1000000` 

  - перемещаемый:

    - подгружается в память по новому случайному адресу

    - не отличаются от разделяемыых объектных файлов ничем кроме наличия прописанного динамического загрузчика

    - компилировать с флагами `-fPIE -pie`: `-fPIE` - генерировать код ассемблера для позиционно независимых файлов (position independent executable), `-pie` - для компоновщика сделать на выходе перемещаемый исполняемый файл

    - `objdump -f app` -> `DYNAMIC` = адрес размещения программы в памяти должен быть определён при загрузке программы в память

    - `objdump -h app` -> адреса секций даны в предположении, что программа начинается с нулевого адреса

- статически скомпонованный файл:

  - не требует загрузки динамических библиотек, расчитан на загрузку с фиксированного адреса

  - может не иметь таблицы символов, к тому же она и не нужна -> удалить её `strip -s app`

  - компилировать с флагом `-static`

  - файл большого размера, так как код всех библиотек непосредственно вставляется в исполняемый файл

  - требуется статическая версия стандартной библиотеки С - `libc.a` - по пути `usr/lib64`; `.a` - архивные / библиотечные файлы (в Windows - `.lib`)

  - архивные файлы являются архивами из объектных файлов, снабжены своей таблицей символов

  - `objdump -f /usr/lib64/libc.a` - заголовок архива

  - `ar r libsum.a sum.o` - добавить / заменить объектный файл в архиве

- разделяемый объектный файл (shared object), то есть динамическая библиотека:

  - в отличие от перемещаемого исполняемого файла предназначен для загрузки в память других программ, поэтому не имеет точки входа, даже если текст программы содержит `main`

  - компилировать с флагами `-fPIC -shared`: `-fPIC` - генерация позиционно независимого ассемблерного кода; `-shared` - компоновщик должен создать разделяемый объектный файл

  - `objdump -f app` -> как у перемещаемого объектного файлоа, только start point = 0


Преимущества динамической компоновки:

- код библиотеки один раз загружен в память и используется всеми процессами в системе

- исполняемый файл меньшего размера

- независимое обновление динамической библиотеки, исполняемые файлы исползуют её новую версию

Недостатки динамической компоновки:

- зависимость от динамических библиотек, которые могут зависеть от ОС; для максимальной переносимости стоит компоновать программы статически
